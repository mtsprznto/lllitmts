# PRD-006 — Build Windows: `nodeLinker: hoisted` para el adapter Vercel

> Estado: **FIX APLICADO + REINSTALL VERIFICADO** — 17-oct-2026 16:47: `.modules.yaml` → `"nodeLinker": "hoisted"`, 0 symlinks top-level, `.pnpm/` solo `lock.yaml`. Pendiente: confirmar `pnpm build` exit 0 (criterios §5).
> Correlativo: `PRD_006` (antes de tocar código, obligatorio por `AGENTS.md`).
> Fecha: 17-oct-2026. Independiente de `PRD_005` (gallery); este PRD es de infraestructura de build.

## 1. Contexto y problema

`pnpm build` en Windows (pnpm 11.13.1, Node v22.22.1, shell del usuario) falla al final del build, en el hook `astro:build:done` del adapter:

```
[ERROR] [@astrojs/vercel] An unhandled error occurred while running the "astro:build:done" hook
EPERM: operation not permitted, symlink '.pnpm\resend@6.17.2\node_modules\resend'
  -> 'D:\...\lllitmts\.vercel\output\functions\_render.func\node_modules\resend'
    at async copyDependenciesToFunction (.../@astrojs/vercel/dist/lib/nft.js:54:26)
```

El sitio compila bien (server entrypoints 2.61s). Explota al empaquetar la función serverless para `.vercel/output` — nada del código del proyecto está involucrado.

## 2. Causa raíz (verificada en esta máquina)

1. `node_modules` está instalado con el layout **aislado** de pnpm (`node_modules/.modules.yaml` → `"nodeLinker": "isolated"`): las entradas top-level son junctions/symlinks hacia `.pnpm/...`.
2. `@astrojs/vercel` (`dist/lib/nft.js` → `copyDependenciesToFunction`) invoca `copyFilesToFolder()` de `@astrojs/internal-helpers`, que **replica el layout** dentro de `.vercel/output/functions/*_render.func/` con `fs.symlink()` para cada archivo cuyo `realpath !== origin` — es decir, todo lo que cuelga de `.pnpm/`.
3. En Windows, `fs.symlink()` requiere el privilegio `SeCreateSymbolicLinkPrivilege` (Developer Mode ON o proceso admin). Los **junctions NO lo requieren** — por eso `pnpm install` funciona en la misma máquina, pero el adapter muere con `EPERM`. Evidencia empírica (`node` de Windows 22.22.1, scratch `.tmp-symtest/symcheck.cjs`):

   ```
   symlink dir : FAIL EPERM
   symlink file: FAIL EPERM
   junction    : OK
   ```

4. Upstream `withastro/astro@main` (revisado 17-oct-2026): `copyFilesToFolder` sigue con `fs.symlink()` sin fallback y el adapter no expone opción para desactivarlo → no existe versión a la que actualizar que lo arregle.
5. **El fix previo era inefectivo**: `.npmrc` con `node-linker=hoisted` (commit `611007e`, 09-ago-2026). pnpm 11 **ignora** settings de layout en `.npmrc` (docs: "Only auth and registry settings are read from `.npmrc`… `nodeLinker` can only be set in `pnpm-workspace.yaml`"). Probado empíricamente con pnpm 11.13.1: `.npmrc` → `pnpm config get node-linker` = `undefined`; `pnpm-workspace.yaml` → `hoisted`. Por eso el install del 08-oct siguió generando layout aislado y el build de hoy volvió a fallar.

## 3. Fix

- `pnpm-workspace.yaml` → **`nodeLinker: hoisted`** (ubicación oficial del setting en pnpm 11).
- Eliminar `.npmrc` (su único contenido era ese setting inerte + comentarios engañosos).
- Reinstalar `node_modules` **una vez** desde Windows (paso de usuario, §6).

Con `hoisted` no hay reparse points (ni `.pnpm/`): `fs.realpath(origin) === origin` → `copyFilesToFolder` usa `fs.copyFile` y **nunca** llama `fs.symlink` → el `EPERM` es imposible por construcción. Bonus: `.vercel/output/…/_render.func/` queda con copias reales (self-contained), más robusto para deploy prebuilt.

## 4. Alcance

- **IN**: `nodeLinker: hoisted` en `pnpm-workspace.yaml`; eliminar `.npmrc`; sección "Build (Windows)" en `docs/PROJECT.md`; este PRD.
- **OUT**: parchear `@astrojs/internal-helpers` (se pierde al reinstalar — antipatrón); activar Developer Mode (alternativa de máquina, no de repo; queda como plan B); deploy/CI (Vercel remoto: Linux permite symlinks siempre → inocuo).

## 6. Verificación (usuario — Windows PowerShell, raíz del repo)

```powershell
Remove-Item -Recurse -Force node_modules      # si falla con junctions: cmd /c "rmdir /s /q node_modules"
pnpm install
pnpm config get node-linker                   # → hoisted
Select-String nodeLinker node_modules\.modules.yaml   # → "nodeLinker": "hoisted"
pnpm build                                    # → exit 0
```

Plan B (si algo del reinstall se traba): **Developer Mode ON** (Configuración → Sistema → Para desarrolladores) — con eso incluso el layout aislado compila, porque `fs.symlink` queda permitido. Complementario, no necesario una vez aplicado hoisted.

## 7. Riesgos

- `hoisted` cambia el layout de `node_modules` (plano, estilo npm): más entradas top-level, hard links del store (mismo disco `D:` ✓). Sin efecto en runtime ni en dev.
- `overrides`/`allowBuilds`/`minimumReleaseAgeExclude` del yaml: ortogonales al linker, no se ven afectados.
- El artefacto `.vercel/output` local queda con copias (no symlinks) → ligeramente más pesado, más portable.
